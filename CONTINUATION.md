## Decoupled browser-lifecycle architecture implemented and verified

The browser process lifetime is now completely decoupled from task lifetime:
- **Runtime ownership:** `PlaywrightBrowserRuntime` manages persistent Chromium process infrastructure.
- **Worker ownership:** Workers lease isolated browser sessions (`BrowserContext` + `Page`) via `acquireSession()`.
- **Session cleanup:** Task completion/cancellation releases the worker's session resources (`BrowserContext.close()`) without killing the persistent Chromium process.
- **Application shutdown:** The Chromium process closes exclusively on application/runtime shutdown (`shutdown()`) or irrecoverable disconnection.
- **Window and viewport stability:** Measured across sequential headed tasks — Chromium launch count = 1, viewport dimensions stable at 1280×720, OS window bounds and position stable down to the exact pixel (width 1282, height 800, screenX 22, screenY 39), zero leaked contexts.
- **Concurrent isolation verified:** Two concurrent worker sessions in one Chromium process maintain isolated contexts, pages, and observation/action state. Closing/cancelling one session does not terminate or affect the other.
- **No-effect recovery verified:** Bounded no-effect scenario successfully triggered optional perception, recorded no-progress, and failed truthfully with stalled status, without capture/freshness errors.

### World / execution invariants

- Resources become world-visible as acquired before observers execute; synchronous reentry through another runtime cannot acquire the same resource.
- Execution plans copy resource arrays. Task-creation and supervision observers receive detached data; observer mutation cannot change execution identity, objective or downstream attribution.
- Preparation/start failures terminalize submitted tasks and release newly registered unused task/worker-owned resources, preserving unrelated registrations.
- Maestro's nested child path now handles preparation/start rejection and cancellation without leaving assigned child tasks or unused child-owned resources behind.
- Automatic Goal satisfaction requires an active Goal and a nonempty set of satisfied, evidence-backed required criteria. Late evidence cannot revive cancelled/failed/paused/blocked/waiting-user Goals; optional-only false criteria cannot imply success.

### Parallel runtime

`WorkerRuntime(world, { maxConcurrentExecutions })` defaults to four active executions. Overflow throws `RuntimeCapacityError` before execution mutation; this is fail-fast admission, not a hidden queue. Reservations precede callbacks. Cancellation retains capacity and resource ownership until actual settlement/cleanup. Deferred-promise tests prove real overlap, rejection, isolation and reclamation.

Limits: capacity is per runtime, not per World or distributed; a parent orchestrator occupies a slot. Resource exclusion spans runtimes sharing an in-memory World, but external process isolation is not provided. Maestro still delegates one Cody child rather than planning a concurrent specialist team.

### Event-driven supervision foundation

Cancellation has immediate user priority. Routine tool activity does not wake Maestro. Bounded 256-entry notification windows deduplicate forwarded events and corresponding wakes; World remains authoritative. Observers cannot alter outcome and rejected asynchronous callbacks are contained.

Limit: the callback is an integrated runtime seam, not yet a production Maestro attention queue/reasoning consumer. No LLM polling or automatic retries of unknown mutating actions were added. Notification deduplication is bounded, not permanent exactly-once delivery.
