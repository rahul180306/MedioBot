## 2026-10-23 — Atomic approval-cancellation boundary

- Code review found that `composition.cancel()` cancelled in-memory/persisted tool approvals before asking `RuntimeTaskSubmission` to cancel the task. A LangGraph interrupt has already settled its WorkerRuntime run, so the runtime could reject cancellation after the approval had irreversibly changed to `cancelled`.
- Reordered the composition operation: cancellation must first be accepted by the execution owner; only then are matching approval waiters cancelled. If a suspended run cannot accept cancellation, the Main Chat API returns `409 cancellation-unavailable`, the task remains `waiting_approval`, and the durable approval remains `requested` and restartable. The response does not falsely claim success.
- Added this assertion to the production `/api/turns` restartable-approval flow in `apps/command-center/tests/runtime/cody-turn.test.ts`; it calls `POST /api/tasks/:childTaskId/cancel` for the actual approval-owning Cody child while both child and parent are durably waiting. It verifies the HTTP failure and unchanged child approval/task records, then restarts and resumes the exact approved action once.
- Verification: Command Center backend/persistence suite **323 total / 315 passed / 0 failed / 8 skipped**; all 11 workspace typechecks passed; `git diff --check` passed. No provider request was made.
- Limit: this fixes the partial-mutation defect and preserves recovery; it does not yet implement cancellation of a graph already suspended on a durable approval. That behavior remains a distinct task-control gap and must not be described as supported.

## 2026-10-23 — Approval cancellation/resume race

- Root cause: LangGraph approval interrupts have no active WorkerRuntime run to cancel. The fallback previously inspected durable/world state and then cancelled approval records without sharing synchronization with the approval HTTP route. Concurrent approval could grant and resume after the cancel check, leaving contradictory task state or a worker running after a cancellation response.
- Added a bounded in-process per-task-family control lock. Child operations resolve to their parent task key. Both normal/suspended cancellation and approval resolution/restart-resume now serialize on this lock; approval re-reads its durable request after acquiring the lock and rejects stale decisions after cancellation. Repeated same-decision recovery remains allowed after an interrupted resume attempt, but is rejected while the owning runtime task is already active to avoid duplicate starts.
- Suspended-approval cancellation now durably cancels eligible paused child/root tasks, cancels pending approvals, preserves completed sibling outcomes, sets world task state, emits attributed terminal events, and flushes the root event journal. It refuses fallback cancellation if any family member is active or not actually approval-paused.
- Controlled production-path regression queued cancellation before a competing approval while holding the family lock: cancellation returned 202, the stale approval returned 409, durable child/root and approval states became cancelled, no protected write occurred, and the Main Chat turn became cancelled. The same test then restarted the application, retried an approved workflow after a simulated transient resume failure, and verified the exact write and verification completed once without repeating Maestro delegation.
- The explicit `/api/tasks/:id/resume` route also uses the same family lock, so queued task restart and cancellation cannot race; it rereads the durable task inside the lock before transitioning state.
- Added explicit cancellation for a reconciled, fully interrupted durable task family. It refuses any family with active runtime tasks or mixed non-interrupted active states; it cancels durable records and group/message state, emits durable attributed task-cancelled product events, and works when process-local World task objects no longer exist. Completed siblings remain untouched.
- Source audit found no production `waiting_input` or non-approval LangGraph interrupt producer. ## 2026-10-23 — Terminal subprocess-tree cancellation

- Confirmed defect: terminal child processes were not placed in an owned Unix process group, while abort handling only killed the immediate child. A descendant could outlive the visible terminal command and become untracked when the root child closed.
- Terminal commands now launch detached on POSIX so the child PID is also the owned process-group ID. Task cancellation terminates that group and escalates after the configured grace period. Windows uses `taskkill.exe /PID <pid> /T`, then `/F` after grace; invocation uses `execFile` without a shell. If Windows tree termination itself fails, a direct-PID signal is attempted, but descendant termination is not claimed.
- Cancellation arriving before the child is registered is retried after spawn/registration. The terminal tool waits for the supervisor's bounded group termination and escalation before it reports settlement. Supervisor records remain counted during cleanup, and are removed only when escalation settles; a process that ignores `SIGTERM` is still targeted by group `SIGKILL` after grace even if its leader exited.
